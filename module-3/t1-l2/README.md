# Оптимизация отдельных компонентов

## Пропускная способность

Основные факторы:
- кол-во партиций
- кол-во продьюсеров
- кол-во консьюмеров

Отправные точки:
- Ожидаемая (требуемая) пропускная способность - T
- пропускная способность 1 продьюсера - Pt
- пропускная способновть 1 консьюмера - Ct

Тогда хорошим приближением для кол-ва партиций является:

> n_partitions = max(n_producers, n_consumers)
> 
> n_producers = Т / Pt
> n_consumers = Т / Ct
> 

Важные моменты:
- увеличить кол-во партиций можно
- уменьшить кол-во партиций нельзя (можно, но с потерей сообщений ?): через создание нового топика и переливкой даннных
- если при обработке используются ключи (partiton_keys), то может нарушиться порядок/схема обработки

### Системные и файловые дескрипторы

Партиции используют файловые ресурсы - `open file handlers`, формула для оценки их числа:

> n_descriptors = n_partitions x ( partition_size / segment_size )
> 

Дополнительно, дескрипторы требуются:
- для поддержания связи с консьюмерами/продьюсерами/другими брокерами
- работы ZooKeeper
- аутентификации

### Пакетная обработка (batching)

Один из способов повысить пропускную способность: пакетная обработка (batching):
- перед отправкой продьюсер группирует сообщения в пачки (batch)

Это снижает кол-во сетевых запросов, повышает пропускную способность, НО увеличивает задержку.

Настройки продьюсера:
- `batch.size` - максимальный размер 1 пакета в байтах
- `linger.ms` - время ожидания перед отправкой батча


### Сжатие сообщений


При передачи сообщений их можно сжимать, за это отвечает настройка `compression.type: (lz4, snappy, zstd, gzip)`

Рекомендации:
- `lz4` - лучший компромис между сжатием и временем обработки
- `gzip` - даёт повышенную нагрузку на CPU
- для продьюсера и консьюмера выбирайте одинаковый тип сжатия, иначе кафка будет перерабатывать данные

### Подтверждение доставки (acks)

> чем выше уровень подтверждения, тем медленнее обработка

Примеры:
- `acks=0` = fire and forget, max throughput
- `acks=1` - запись только в локальный лог
- `acks=all` - подтверждение от всех реплик

хороший материал [conduktor](https://www.conduktor.io/kafka/kafka-producer-acks-deep-dive#acks-overview)


### Размер буфера продьюсера

Существует внутренний буфер продьюсера, где он хранит неотправленные сообщения, его настройки:
- `buffer.memory` - общий объём в байтах
- `max.block.ms` - сколько времени продюсер ждёт, прежде чем бросить ошибку при переполнении буфера

Рекомендации:
- Увеличьте `buffer.memory`, если у вас много партиций или крупные пакеты. Это поможет избежать блокировки продюсера и сохранить стабильную передачу данных.

> блокировки продюсера - запрет отправки сообщений, может наступать при следующих условиях:
> - получение сообщений в момент его отправки (продьюсер ждет подтверждения)
> - переполнение буфера продьюсера
> - обновление метаданных кластера

### Объем выборки консьюмера (fetch)

Чем больше обрабатываемая пачка, тем реже консьюмер обращается к кластеру:
- выше пропусная способность
- увеличенная задержка

Параметры:
- `fetch.min.bytes` - минимальный размер на брокере, который он должен накопить, что отдать консьюмеру
- `fetch.max.wait.ms` - максимальное время ожидания до отправки, если данных недостаточно


### Дополнения

- использовать группы консьюмеров
- кол-во консьюмеров в группе не может превышать кол-во партиций в топике
- Настройте JVM на брокерах

## Цель: уменьшение задержки

Пример концепции:
- партиции и брокеры

чем выше кол-во партиций, тем больше времени уходит на репликацию (по дефолту, она идет в один поток), поэтому рекомендации:
 - снизить кол-во партиций
 - увеличить число брокеров
 - увеличить число поток для репликации `num.replica.fetchers > 1`

> Стоит увеличить num.replica.fetchers (например, до 4), если:
> партиций > 100 на брокер; 
> замечаете высокую задержку у консьюмеров (follower lag).
>

- пакетная отправка:
  - батчи поменьше
  - время поменьше или = 0: `linger.ms = 0`
- cжатие: отключаем или используем `lz4`
- fetch консьюмера: выставялем 1Байт и минимальное время (100ms)
- acks: разумный компромисс `acks=1`, если хочется большего то 0

## Цель: повышение надёжности

- основной момент: репликация, как топиков данных (`replication.factor = 3`), так и внутренних топиков кафки (`offsets.topic.replication.factor = 3`)
- `acks=all` + `min.insync.replicas = 2`
- `retries=бесконечность`

### сбой лидера

при сбое лидера, следующий выбирается из списка ISR (реплики, синхронизированные с лидером)

> Если ISR пустой, и unclean.leader.election.enable = true, лидер может быть выбран из неактуальных реплик, что приведёт к потере данных.

Чтобы не терять данные -> `unclean.leader.election.enable = false` -> только актуальные реплики, могут стать лидером

### сброс на диск

Для надежных топиков можно форсировать сброс на диск при помощи настроек:
- `log.flush.interval.messages = 1`
- или `log.flush.interval.ms = 1000`

Автокомит может приводить к потере данных -> управлять самостоятельно коммитом (`enable.auto.commit = false/true`)

### Exactly Once Semantics (EOS)

Для обеспечения указанной семантики ("ровно один раз") необходимо выставить настройки во всех компонентах

Для продюсера:
- Включить: `enable.idempotence = true`
- Использовать: `sendOffsetsToTransaction()`

Для консьюмера:
- Установить: `isolation.level = read_committed`

Для Kafka Streams:
- Установить: `processing.guarantee = exactly_once`

## цель: высокая доступность

- `acks=all`
- `min.insync.replicas` - можно выбирать так: для высокой доступности = 1, для надежности >= 2
- при восстановлении кафка читает журнал партиций, чтобы ускорить чтение можно увеличить кол-во потоко `num.recovery.threads.per.data.dir -> 4` (если у вас 4 директории)
- автоматическое перераспределение консьюмеров в группе при сбое, чтобы восстановление прошло быстрее (поиск "потерянного" консьюмера) можно уменьшить
`session.timeout.ms` , но слишком маленькое может привести к ложным срабатываниям GC (garbage collector)

Дополнительные параметры:
- `max.poll.interval.ms` — увеличьте, если обработка сообщений занимает много времени.
- `max.poll.records` — уменьшите, чтобы быстрее обрабатывать пакеты и чаще «отчитываться» брокеру.


## цель: обработка больших сообщений

Лучшие рекомендации:
- уменьшить размер сообщения
- сжатие
- отказаться от передачи сообщений в пользу передачи ссылок на них (S3/hdfs)
- фрагментировать сообщения (разделить, а потом собрать)


## Оценка общего размера кластера

> примерная оценка размера = скорость поступления данных[МБ/сек] * период хранения[сек/дни/недели]

Оценка нагрзуки на диск: скорость продьюсеров * `replication.factor=3` (запись на диск для себя и на каждой реплике)

Сетевая нагрузка на чтение: кол-во консьюмеорв * скорость продьюсеров + скорость продьюсеров * `replication.factor - 1` (исключая лидера)
